Installation

Five minutes, and no build step unless you change the UI.

  1. Drop the folder in Put it in resources/[custom]/ and add ensure royal-phone to your server config — after ox_lib and oxmysql.
  2. Pick your framework Set Config.Framework in config.lua to QBX, ESX, OX, ND or STANDALONE. The matching file in bridge/ is the only place framework-specific code lives.
  3. Add the items Copy the two entries from ox_inventory_items.lua into ox_inventory/data/items.lua. The phone will not open without sim_card unless you set Config.RequireSim = false.
The database sets itself up

server/migrate.lua runs sql/royal-phone.sql on every start and creates whatever is missing, so you never run it by hand and never have to run it again after an update. Every statement is CREATE TABLE IF NOT EXISTS, and column additions go through a checked helper rather than a bare ALTER — MySQL has no ADD COLUMN IF NOT EXISTS before 8.0.29 and MariaDB's syntax differs, so it is checked against information_schema instead of attempted-and-ignored. New tables are logged the first time they appear.

No build needed The UI ships pre-built in web/build. You only run npm run build if you edit something under web/src or add icon artwork.

Moving with it open

WASD, sprint and jump stay with the game, so the player walks and drives as normal with the phone up. Weapons, melee and the pause menu are suppressed.

The camera is locked on purpose

The mouse belongs to the phone — it has to, that is how you tap things. So mouse-look is disabled while the phone is open, because every swipe across the screen would otherwise spin the player round. You can move, but not look.

The catch that makes movement work

With input handed back, every keystroke reaches both the UI and the game — typing "was" into a message would also send the ped walking.

So the UI reports caret focus to Lua and Lua drops all control for exactly as long as a text box is focused. focusin / focusout rather than focus / blur, because only the former bubble and the inputs are deep in the tree:

// web/src/components/NuiBridge.jsx
const editable = (node) =>
    node.tagName === 'INPUT' || node.tagName === 'TEXTAREA' || node.isContentEditable;

document.addEventListener('focusin', (e) => editable(e.target) && fetchNui('typing', { active: true }));
document.addEventListener('focusout', () => fetchNui('typing', { active: false }));

Set Config.AllowMovement = false for the old behaviour, where the phone takes everything and the player stands still until it closes.

Call mode and peek mode take no mouse at all

Both are display-only: the phone is on screen, the game keeps the cursor, and the player carries on. That is why answer and decline are keybinds rather than buttons — see Calls.

SIM cards

The phone is hardware. The SIM is the identity.

With Config.RequireSim, the number, contacts, messages, groups, documents and Lifeinvader accounts all belong to the SIM card rather than the character. The card carries a serial in its ox_inventory metadata, and everything in the resource is keyed to that serial.

The card goes inside the phone

The phone item is an ox_inventory container with a single slot — that slot is the SIM tray. Open the phone in your inventory and drop the card in.

Why a plain item search does not find it

A container is a separate inventory with its own id. Searching the player's own inventory for the SIM reports zero even with a card sitting in the phone, which is exactly the bug this resolves. The lookup now reads the phone's container first (GetContainerFromSlot, which builds the inventory if the player has never opened it) and only then falls back to a card loose in their pockets — so both arrangements work.

Give the phone's container a whitelist = { 'simcard' }, or the single slot will happily hold a burger.

A blank card registers itself to whoever first puts it in a phone — serial, number, and a description on the item showing the number. From then on the card is the phone account, wherever it ends up.

Slot data is a live reference

GetSlotWithItem hands back the actual table out of ox_inventory's item list, not a copy. Writing a field onto it — or editing its metadata in place — changes the player's inventory before SetMetadata has validated anything, and that edit gets persisted. Both are copied before use here.

This is the point of the feature

Put someone else's SIM in your phone and you are reading their messages. Settings › SIM Card says whose card it is and marks it "Borrowed" when it is not yours. Texts you send from a stolen card still go out under your name — the card is the account, not the identity.

What deliberately stays with the character

  • Banking. Money is the player's, not the card's — a stolen SIM must not hand over somebody's bank account.
  • The home screen layout, which is per-character KVP.

Never let the SIM item stack

Each card holds its own identity in metadata, so stacking would merge two phone numbers into one slot. The definition in ox_inventory_items.lua sets stack = false — keep it that way.

How the code sees it

server/identity.lua is the only file that knows any of this exists. Everything else asks it who the caller is and gets back an opaque owner key — the SIM serial with cards on, the character's identifier with them off:

-- anywhere on the server
local identity = Identity.get(src)
if not identity then return end   -- no phone, or no registered SIM

-- identity.owner   whose phone this is — key every query on this
-- identity.number  the phone number
-- identity.name    who is HOLDING it (not who the card belongs to)
-- identity.serial  the SIM serial, or nil when SIMs are off

Because the whole resource already keyed on "whose phone is this", swapping the meaning of that key from character to card was the entire change — no app needed to know.

How the phone works

One React tree, one Lua file each side, and a strict rule about who talks to whom.

The shape of it

client/main.lua

Owns opening, closing, focus, the keybind and the animation. Every message to the UI goes through it.

server/*.lua

All database access and anything a client must not be trusted with — numbers, messages, calls, social, documents.

bridge/

Five framework adapters, client and server. The only files that know what QBX or ESX is.

web/src

The interface. NuiBridge.jsx is the single place that listens to Lua; nothing else in the tree does.

What happens when a player opens it

  1. The keybind or /phone hits Toggle() in client/main.lua.
  2. It checks the item, whether the player is dead or cuffed, then fetches all the data in three awaits: getData, li:getData and docs:getData.
  3. SetNuiFocus(true, true), play the animation, then SendNUIMessage with a single bootstrap payload.
  4. NuiBridge hands each slice to its store and the UI renders.
  5. Two threads start and live only as long as the phone is open — one per-frame to swallow the pause menu so Escape reaches the UI, one per second for the clock.
No polling

Player data is fetched once per open, never on a loop. If something changes server-side while the phone is up — a new message, an incoming call — the server pushes it with a TriggerClientEvent, and the client forwards it as its own NUI message.

The two directions

Lua → UI

Lua calls SendNUIMessage({ action = 'name', data = ... }); React listens with the useNuiEvent hook. Every listener in the project lives in web/src/components/NuiBridge.jsx so the wiring stays in one file.

-- client/main.lua
send('notify', { app = 'bank', title = 'Deposit', content = '$2,500 received' })
// web/src/components/NuiBridge.jsx
useNuiEvent('notify', (data) => notify(data || {}));

UI → Lua

React calls fetchNui(name, data, mockResult); Lua answers with RegisterNUICallback. The third argument is what the call resolves to in a plain browser, which is what makes the whole UI runnable outside the game.

// anywhere in the UI
const result = await fetchNui('docs:save', { id, title, body }, { id: 1 });
-- client/main.lua
RegisterNUICallback('docs:save', function(data, cb)
    cb(lib.callback.await('royal-phone:server:docs:save', false, data) or false)
end)

Home screen & layout

Folded, the grid is 4×5 — twenty slots a page. Unfolded, the same order reflows into a wider grid: columns are measured from the actual frame width and rounded down to a multiple of four, so a viewport too narrow for a true 3× degrades to eight columns rather than squashing twelve.

Why pages are stored, not derived

The layout is an explicit pages: string[][] rather than a flat list that gets chunked. That is deliberate: an empty page has to be able to exist, because that is exactly what dragging an icon off the right edge creates. A derived layout cannot represent "page 3, currently empty, waiting for you to drop something on it". Empty pages are tidied up when edit mode ends.

Moving things

  • Hold an icon to enter edit mode, then drag it.
  • Hold it against the right edge to move to the next page, or make one past the last.
  • Against the left edge to go back — except on page one.
  • Four dock slots sit below, stored alongside.

Persistence

Layout and settings save per character into one KVP blob — royal-phone:layout:<citizenid> — with a 250 ms debounce. One write, one read, no database round trip. The unfolded view flattens and re-chunks for display but always persists in the canonical folded shape, so flipping out and back never rewrites a player's layout.

Sizing & CSS variables

Nothing in the UI is a hard-coded pixel size. Everything is a fraction of the panel width.

web/src/utils/usePhoneMetrics.js is the single source of truth for geometry. It measures the viewport, works out the frame, and publishes a set of CSS custom properties that the rest of the UI sizes off. Change a ratio there and the whole phone follows at every resolution.

Player-facing zoom

Settings › Wallpaper & Zoom offers Default / Medium / Large — 100 %, 115 % and 130 %. 100 % is the base frame; it only scales up. App screens are wrapped in ScreenScale, which applies CSS zoom against a 380 px reference width, so a 15 px label stays 15 px relative to the phone at any size. Settings saved before the size range was rebased are clamped into range on load.

Flip-out

EXPAND_FACTOR = 3. Folding and unfolding is a single spring on width, x and y together — one animation, not three racing each other. The phone rests bottom-right when open; a call or a notification parks it at one of two lower heights (see Calls).

Colour

  • Sky (sky-400 / sky-500) is the phone's accent — unread badges, active states, primary buttons.
  • Emerald means money or "open"/live.
  • Rose is destructive only.
  • Surfaces are white at low alpha over the app's own background: 0.05 for nav, 0.06 for cards, 0.07 for inputs.

Full bleed and opaque

Apps run edge to edge with the status bar and home indicator drawn on top of them, so the chrome always sits on the app's own colour. That is why every app sets a background in its config entry rather than relying on a shared one.

The zoom rule

Read this before writing an app screen

Nothing inside ScreenScale may use framer-motion's layout prop or drag.

ScreenScale applies CSS zoom. framer-motion measures elements with getBoundingClientRect(), which returns zoomed coordinates, then applies the resulting transform in local space. The two disagree by exactly the zoom factor, and the element flies off, jumps, or animates from the wrong place.

This has bitten this project four separate times — a toggle knob that shot off the switch, notification entries that jumped on mount, toasts that glitched, and home icons that "assembled" themselves on open.

What to do instead

  • Animate x / y / opacity / height explicitly rather than letting layout work it out. The Toggle in _shared.jsx animates x: 0 → 20 for this reason.
  • If something genuinely needs layout or drag, lift it out of the zoom box and size it off --pw instead — that is what the toast stack does.
  • Home icons scope it: layout={editMode ? 'position' : false}, so the measurement only happens while dragging is actually possible.
Why zoom at all

ScreenScale measures its parent with a ResizeObserver and writes real pixel sizes, because percentage-based scaling resolves differently across Chromium versions — and CEF is not the Chromium you tested in.

Add an app

The whole contract is one entry in one file, plus a component.

  1. Write the screen Create web/src/apps/MyApp.jsx. It receives two props: app (its own config entry) and initial (the route payload from a notification, if it was opened by one). Start from the skeleton below.
  2. Lazy-import it In web/src/config/apps.jsx, next to the others: 
    const MyApp = lazy(() => import('../apps/MyApp'));
  3. Point its entry at the component Find the existing entry in APPS and add component and background. Apps without a component render StubApp ("Coming soon"), which is how the unbuilt ones behave today.
  4. Rebuild npm --prefix web run build. Done — it is on the home screen.

The config entry

{
    id:         'garage',          // what the saved layout stores — NEVER rename a live one
    label:      'Garage',          // caption under the icon
    icon:       Car03Icon,       // Hugeicons glyph, used when there is no artwork
    gradient:   'bg-gradient-to-br from-neutral-300 to-neutral-600',

    background: 'bg-[radial-gradient(120%_80%_at_50%_115%,#101c33_0%,#070b14_55%,#03050a_100%)]',

Do not rename ids

The id is what every player's saved layout refers to. Renaming one on a live server drops that app out of everybody's home screen and into the "new app" pile.

Screen skeleton

Copy this and you get the chrome padding, the header, the scroll behaviour and the bottom nav right on the first try.

import React, { useState } from 'react';
import { HugeiconsIcon } from '@hugeicons/react';
import { Home01Icon, Settings01Icon } from '@hugeicons/core-free-icons';

const TABS = [
    { id: 'home',     label: 'Home',     icon: Home01Icon },
    { id: 'settings', label: 'Settings', icon: Settings01Icon },
];

export default function MyApp({ initial }) {
    const [tab, setTab] = useState(initial?.tab ?? 'home');

    return (
        <div
            className="flex h-full w-full flex-col"
            style={{ paddingTop: 'var(--status-h)', paddingBottom: 'var(--chrome-b)' }}
        >
            <header className="flex shrink-0 items-center gap-1 px-5 pb-3 pt-1">
                <h1 className="flex-1 truncate text-[26px] font-bold leading-tight tracking-tight text-white">
                    My App
                </h1>
            </header>

            <div className="royal-scroll min-h-0 flex-1 overflow-y-auto px-5 pb-2">
                {/* content */}
            </div>

            <nav className="mx-4 mb-1 flex shrink-0 items-center justify-around rounded-3xl bg-white/[0.05] p-1.5">
                {TABS.map((item) => {
                    const active = tab === item.id;

                    return (
                        <button
                            key={item.id}
                            onClick={() => setTab(item.id)}
                            className={`flex flex-1 flex-col items-center gap-1 rounded-2xl py-2 transition ${
                                active ? 'bg-white/[0.10] text-white' : 'text-white/40 hover:text-white/70'
                            }`}
                        >
                            <HugeiconsIcon icon={item.icon} size={19} strokeWidth={active ? 2 : 1.7} />
                            <span className="text-[10px] font-medium">{item.label}</span>
                        </button>
                    );
                })}
            </nav>
        </div>
    );
}

Data & NUI callbacks

Adding a server-backed feature, end to end.

  1. Add the table Append to sql/royal-phone.sql as CREATE TABLE IF NOT EXISTS, so re-running the file is always safe.
  2. Register the server callback In its own file under server/ if it owns tables of its own — that is why lifeinvader.lua and documents.lua are separate — then add it to server_scripts in fxmanifest.lua. 
    lib.callback.register('royal-phone:server:garage:getData', function(src)
    local player = getPlayer(src)
    if not player then return nil end

    return { vehicles = MySQL.query.await(
        'SELECT plate, model FROM player_vehicles WHERE citizenid = ?',
        { player.identifier }
    ) or {} }
end)
  3. Bridge it on the client A read goes in the bootstrap; a write gets its own RegisterNUICallback. 
    -- inside Open(), with the other awaits
local garage = lib.callback.await('royal-phone:server:garage:getData', false)

send('bootstrap', { data = cachedData, lifeinvader = li, documents = docs, garage = garage })
  4. Make a store and hand it the slice Add the store in web/src/state/, then two lines in NuiBridge.jsx: 
    const setGarageData = useGarageStore((s) => s.setData);
// ...inside the bootstrap listener
if (payload?.garage) setGarageData(payload.garage);
  5. Seed it for the browser Give the store a loadMock() and call it from app.jsx. Without this the app is blank in the dev server, and you will end up testing in-game for no reason.
Trust nothing from the client

Always resolve who is asking from src on the server, never from the payload. Lifeinvader resolves which account a request acts as from the caller's identifier, so a player cannot post as someone else's handle. Documents re-checks access against the database on every write, even though it also tells the client what it may do — that flag is for greying out buttons, not for authorisation.

Never return a new object from a selector

A selector that builds its result — useStore((s) => s.book()) — returns a fresh array every call, React sees the snapshot change forever, and the tree unmounts with "getSnapshot should be cached". Select the raw fields and derive in a useMemo:

// wrong
const book = useFishingStore((s) => s.book());

// right
const species = useFishingStore((s) => s.species);
const caught  = useFishingStore((s) => s.caught);
const book    = useMemo(() => build(species, caught), [species, caught]);

Notifications

Toasts drop in under the status bar and lift back out the same way. Swipe up or hit the × to dismiss; tapping one opens the matching app.

Sending one

-- client
exports['royal-phone']:Notify({
    app      = 'messages',   -- app id: drives the icon and colour
    title    = 'Mikkel',     -- bold first line
    content  = 'meet me at the pier',
    avatar   = nil,           -- image url shown instead of the app icon
    duration = 5000,          -- 0 keeps it up until dismissed
    sound    = true,          -- false adds it silently
    route    = { number = '555-0192' },   -- see below
})

-- server
exports['royal-phone']:Notify(source, data)

Routing into a screen

A route is handed to the app as its initial prop when the notification is tapped, so it can open the right page instead of its front page. Tapping also closes the notification centre.

AppRoute
messages{ number = '555-0192' } — opens that conversation. Incoming texts set this for you.
dialer{ tab = 'calls' | 'keypad' | 'contacts' }
documents{ id = 12 } — opens that document. Invites set this for you.

To support routing in your own app, just read initial: useState(initial?.tab ?? 'home').

The notification centre

The bell opens it: a row of quick toggles (sounds, do not disturb, airplane, rearrange apps, settings), a divider, then the list. Two or more consecutive notifications from the same app collapse into one card with a count and a summary line — tap to expand the entries or clear the stack. "History" flips between everything and unread only.

Home-screen bubbles

Every app carries a red bubble while it has an unacknowledged notification, merged with its own unread counts (mail, missed calls). Opening the app clears it — AppHost calls markAppRead on mount, so you get this for free.

Peeking

A notification arriving while the phone is pocketed makes the phone itself peek up from the bottom edge showing the banner, then drop back once the toast expires — or after 6 s, whichever is first.

Why the 6 s cap

The phone has no NUI focus while peeking, so a duration = 0 notification would otherwise pin it on screen with no way for the player to dismiss it. Sticky notifications are still waiting in the tray when the phone is next opened.

Calls

Voice runs through pma-voice. The step that matters is the one in the middle.

The flow

  1. Caller dials — the server reserves a voice channel and rings the receiver. The caller sits on Ringing…; nothing is connected yet.
  2. Receiver answers — royal-phone:server:answerCall. Only now does the server confirm the pickup to both clients, and only then does either one join the channel. Both ends being handed the same channel number is what actually connects them.
  3. Either side ends it — both are taken off the channel together, and the caller is told why (declined, unavailable) rather than the call silently vanishing.
The UI never connects itself

It stays on "ringing" until the server says otherwise, because the caller has no way of knowing the other end picked up. A screen that claims to be connected while no voice channel exists is worse than one that admits it is still ringing — that was the original bug: the receiver answered, the caller's UI went green, and no channel was ever joined.

-- config.lua
Config.Voice = 'pma-voice'   -- or 'none' to run the UI with no audio

pma-voice is optional and guarded with a GetResourceState check, so it is not a hard dependency and load order does not matter.

A call keeps running wherever the player goes. The home indicator tucks a full-screen call into the green status-bar chip so the rest of the phone stays usable, and pocketing the phone drops it to call mode — parked low at the bottom of the screen, chip still ticking, and it will not go away until the call ends.

Call mode and peek mode never take the mouse

Both are display-only. The phone is on screen, the game keeps the cursor, and the player carries on driving or shooting. Answer, decline and hang up are keybinds, shown on the card itself.

The apps

Implemented: Phone, Messages, Bank, Gallery, Lifeinvader, Fishing, Documents, Calculator and Settings. Everything else renders StubApp.

The ids are: calculator documents doj fishing bank gallery garage lifeinvader music news estate settings ventures underground hustlr cliq weather dialer messages contacts browser camera.

The dock is Phone → Messages → Contacts → Camera, set by DEFAULT_DOCK in phoneStore.js. A player who already has a saved layout keeps theirs — the default only applies to a fresh one, or after Reset.

Camera

The viewfinder is the phone screen. While the camera is open the shell drops the wallpaper and the black backing, so the screen becomes a hole you look through — the player holds the phone up and frames the shot through it, exactly like a real one. The home screen stands down for the same reason: it sits behind the app layer and would show through.

Everything drawn is the furniture around that hole, in the phone's own language rather than a camera app pasted on top of it.

InputDoes
ScrollZoom, 1.0× to 4.0×
Middle clickFlip between rear and selfie
Right clickShutter

Bound on the window rather than on buttons, so the whole screen is the control surface with nothing to aim at. The on-screen shutter, flip and gallery buttons duplicate them rather than replacing them.

client/apps/camera.lua owns the camera itself: a scripted cam attached to the head bone — so the shot rides the ped's animation — aimed from the player's own look input each frame. Selfie mode swings the heading 180° and inverts the pitch; without that a selfie points at the back of their head and tilts the wrong way. Zoom maps onto field of view, 75° wide down to 22° tight.

The one place mouse-look comes back

Everywhere else the phone pins the camera, because the mouse belongs to the UI (see Moving with it open). Here the mouse is how you aim the lens, so client/main.lua skips those DisableControlAction calls while PhoneCameraActive.

Lifetime

The scripted camera lives exactly as long as the app screen does — started on mount, stopped on unmount — so there is no separate state to fall out of step. Pocketing the phone unmounts the app and stops it; Close() in Lua stops it too, as do the character unloading and onResourceStop. A camera left running once the phone is gone would be one the player has no way to switch off.

Capture hides the viewfinder's own chrome for the frame it grabs, or the brackets and buttons end up in the photo, then restores it and files the shot in the Gallery. Needs screencapture running; without it the shutter reports failure rather than saving a blank.

Contacts

Its own dock icon, but not its own implementation: it mounts the exact screen the Phone app used to show inline, through the shared ContactsTab, PhoneNav and useDial exports. Adding, editing, sharing and searching behave identically because there is only one of each.

One bottom bar across three apps. Calls, Keypad, Messages, Contacts — the same four slots wherever you are standing, with the current one highlighted. Calls and Keypad are screens inside the Phone app; Messages and Contacts are apps of their own, so PhoneNav routes to whichever owns the tab you tapped. Nothing is highlighted mid-call, because the call is not one of the four.

Where a call from Contacts goes

The Phone app renders the call itself, so it dials minimized and owns the screen. Contacts has no call UI, so it dials un-minimized and hands over to the global call overlay — without that split, a call placed from Contacts would show nothing but the status-bar chip.

Phone & Messages

Deliberately built as a pair: same header, same search field over plain avatar rows, same four-slot bottom nav. The Phone app's Messages tab is a shortcut into Messages; Messages' Calls tab is a shortcut back. Messages tabs are All / Unread / Groups / Calls, with a tick in the header that marks everything read.

Messages supports group threads, emoji, photos from the Gallery and voice notes, with TODAY / YESTERDAY / weekday / date dividers. Groups have an owner: they can rename, invite, kick and delete, while members can only leave. Emoji are a curated set in web/src/config/emoji.js with a Recent tab driven by a per-character usage tally — a picker library like emoji-mart ships about a megabyte of index data, which is a bad trade for a bundle read off disk on every open.

Share in Contacts offers a contact — or your own card, from My Cards — to a player standing next to you. They get a dialog and must accept before anything is written: pushing a contact straight into someone's phone is not something they agreed to, and it made share a way to spam anyone standing near you. One pending offer per person, expiring after 30 s.

The server measures the distance itself and reads the number out of your contact list rather than the payload, so this cannot be used to inject contacts into an arbitrary player. On accept, only the offer the server recorded is trusted — the client's payload is ignored entirely.

Texting someone new

useThreads only builds conversations out of messages that already exist, so texting a contact you have never texted selected a thread that was not there and silently dropped back to the list — which looked exactly like the message button doing nothing. A conversation with no history is now synthesised empty so that first message is possible.

Bank

Balances come from the framework bridge, so QBX cash and bank are live with no extra wiring. Transfer moves money for real: the server debits the sender first and aborts if the balance cannot cover it, so a failed transfer never credits anybody. Sending to an offline character parks the amount in royal_phone_bank_pending and credits it on their next phone open rather than dropping it.

Activity comes from royal_phone_bank_transactions — the phone's own ledger, deliberately separate from the framework's money log. Transfers write themselves in; hook payroll, shops or your banking resource in with the export:

exports['royal-phone']:AddTransaction(source, 'Paycheck', 1850)
exports['royal-phone']:AddTransaction(source, 'Vehicle fuel', -93)  -- negative = money out

Money movement goes through Bridge.MoveMoney(src, account, amount, reason) — 'cash' or 'bank', negative to take away, returning false when the player cannot cover it. QBX, ESX and ND are implemented; ox_core only does cash (it has no bank of its own) and standalone returns false.

Gallery

Groups shots into day sections, stamps each thumbnail with its time, and its viewer steps between photos showing the full date. "Send in a message" carries the photo into Messages, where it waits above the composer until a conversation is picked. Gallery photos are also the picture source for contacts and Lifeinvader posts.

Lifeinvader

The city's social network, with its own bottom navigation: feed (Following / Live / Discover), stories, marketplace, compose, search, notifications and settings. A character signs up with a handle, display name, picture and bio, and can hold several handles and switch between them. Six royal_phone_li_* tables back it.

Live is streams only — ordinary posts never appear there. Streams come from live in the store: { id, handle, name, title, viewers, thumb, url }.

It is live now

The phone fetches once per open and never polls, which meant a feed opened five minutes ago was five minutes stale and you never saw anyone else's posts at all. The server broadcasts a bump whenever anyone posts, likes, comments, follows or lists, and each client re-pulls.

Why the bump is coalesced

The bump goes to everyone. On a busy server that would turn every like into a simultaneous set of queries from every open phone, so the client collapses them to one pull per 1.5 s and skips it entirely unless that player's phone is actually on screen to show the result.

The account directory

Search and Discover read people — every handle on the server — rather than deriving people from whoever happened to appear in your feed. Someone who has never posted can now be found and followed; before, they were invisible, which is why following anyone was effectively impossible.

Notifications

Likes, comments and follows file a row in royal_phone_li_notifications and push a phone notification to the owner if they are online. Never for your own activity. Opening the screen marks them read.

Posts take a gallery photo or a pasted link. utils/embed.js works out what a link is: images and video files render inline, YouTube renders as a thumbnail that swaps to a player on tap — a feed of live iframes would initialise every player at once — and anything else becomes a link card.

Fishing

Four tabs: Home (level, rank with an XP bar and the next rank, biggest and rarest catch, totals, your boat, recent catches), Workshop (harvesting gear, equipment catalog with equipped rod/bait slots, All / Rods / Bait filters), Zones (open zones with what is biting; locked ones show their level requirement) and Catches (the bucket, with sell-all).

Reads fishingStore, fed through the bootstrap payload. Tapping an open zone drops a waypoint. RANKS and BOAT_LEVEL in the store set the rank titles and the boat unlock — change them there, not in the app.

Documents

Write a document, pick a banner, invite other numbers to read or edit. The list shows each document with its banner fading in from the right; inside, the same banner runs behind the header and falls away into the page.

The editor is contentEditable + execCommand: bold, italic, underline, strikethrough, bullets, numbering, quote, and Body / Title / Heading / Subheading blocks. Deprecated API, but the only rich-text primitive every Chromium build implements identically, and it keeps an editor library out of a bundle read off disk on every open. The surface is uncontrolled on purpose: re-rendering a contentEditable from React state puts the caret back at the start on every keystroke.

Document HTML is untrusted

A document is written by one player and rendered inside another player's NUI, so its markup is untrusted input coming back out of the database. utils/richtext.js rebuilds it from an allow-list on the way in and on the way out, and pastes are forced to plain text. Tags outside the list contribute their text but not themselves; attributes never survive at all. If you extend the editor, add to ALLOWED_TAGS — do not bypass the sanitiser.

Saves debounce at 800 ms and flush when the screen closes.

Sharing is contacts and nearby only

The panel has those two tabs and no free-text number field, and the server enforces the same rule rather than trusting the client — a saved contact, or a player within Config.NearbyRange. An open number box would also have been a way to discover which numbers exist by trying them.

The owner alone manages the guest list and is the only one who can delete — for an invited player, delete means leave. Banners are CSS gradients in web/src/config/banners.js, stored as a short id, so no banner can 404 on a document written months ago. Add one to that array and it appears in the picker.

Calculator

Display, tape and keypad. Arithmetic runs on an explicit accumulator rather than by parsing a string, so nothing resembling eval goes near player input. AC turns into a backspace once there is a number to trim, % takes a percentage of the pending left-hand side (200 + 10 % is 220, not 200.1), and the keyboard drives all of it. The tape keeps the last 30 results — tap one to put it back in the display. Nothing persists.

Settings

Wallpaper & zoom, sounds and volume with a test button, do not disturb, airplane mode, hide previews, and rearranging apps.

Icons, sounds, wallpaper

Icon artwork

Drop <app-id>.webp into web/src/assets/icons/ — bank.webp, doj.webp and so on, matching the id in config/apps.jsx — and it replaces that app's gradient tile on the home screen, the dock, toasts and the notification centre. Apps without a file keep their Hugeicons glyph. Filenames are matched case-insensitively, and an entry can point at a differently-named file with an image field (that is how dialer uses Phonecall.webp).

Sounds

.mp3 files in web/src/sounds/ are bundled and playable by filename. Two are wired up:

FilePlays when
newnotification.mp3Any notification arrives
newmessagesent_inapp.mp3You send a message
ringtone.mp3A call is ringing in — loops until answered, declined or ended

playSound(name) fires a clip once; startLoop(name) / stopLoop(name) run one until something stops it. The ringtone uses the second pair — a one-shot blip would be over before the player had reached for the phone.

Where the ringtone stops

Answer, decline, the caller giving up, and setCall moving the call off incoming for any other reason. That last one is the catch-all: every path that clears or replaces the call runs through it, so no route can leave the ringtone playing.

Settings › Sounds has the mute toggle and volume slider. Pass sound = false on a notification to add it silently.

The glob cache

Icons and sounds are resolved by import.meta.glob at build time, so a missing file costs nothing at runtime and only files that exist are bundled. Two consequences: adding artwork needs npm run build, and if the dev server is already running when you add a file, restart it — Vite caches the glob and you will swear the file is broken.

Wallpaper

Settings › Wallpaper & Zoom takes a direct image URL — it must point at an image file, not the page hosting it. Applied and saved as you type; the Set button just skips the debounce. Leave it empty for plain black. Stored per character with the rest of the settings.

Owner keys

Wherever a table has an identifier column it holds whatever Identity calls the owner — a SIM serial with cards on, a character identifier with them off. The two exceptions are royal_phone_bank_transactions and royal_phone_bank_pending, which are always the character, because money does not move with a stolen card.

The home-screen layout is not in the database — it is a KVP blob (royal-phone:layout:<citizenid>), which is why rearranging apps costs no queries.

Development

npm --prefix web install
npm --prefix web run dev

Open http://localhost:5174. Outside FiveM the UI loads mock data and shows a dev panel: app notifications, four people who can text you (each writes a real thread entry as well as raising the toast), a text storm, a notification burst, an incoming call, and layout reset. Every store is on window.royalPhone for poking at from the console.

Developing against a live server

Point ui_page at http://localhost:5173/ in fxmanifest.lua, work with hot reload, then:

npm --prefix web run build

…and switch ui_page back to web/build/index.html before you ship.

Ship the build

web/build is committed on purpose — that is what makes the resource drop-in for people who never touch the UI. Rebuild it whenever you change web/src.

Performance

  • No polling. Player data is fetched once per open, the clock is pushed on a 1 s tick, and the only per-frame loop (pause-menu suppression) runs solely while the phone is on screen.
  • One app mounted at a time, so timers and subscriptions die with the screen.
  • Code-split screens — the shell boots with the home screen only.
  • Layout writes go to KVP, debounced, never to the server.
  • Geometry is CSS custom properties, so the UI scales with resolution instead of reflowing in JavaScript.
  • Batched queries. Comments, shares and similar are fetched in one pass and bucketed in Lua rather than queried per row.

Gotchas & known gaps

Traps worth knowing

  • framer-motion layout inside ScreenScale — see the zoom rule. This is the single most common way to break a screen here.
  • Tailwind's -translate-x-1/2 plus a framer animate on the same element — framer writes an inline transform that wipes the Tailwind translate, and your centred element is not centred. Wrap it in a static centring div instead.
  • Vite's glob cache — new icons and sounds need a dev-server restart.
  • Selectors that build objects — see Stores.
  • Implicit form submission is unreliable in NUI — wire onKeyDown for Enter explicitly, the way the message composer does.
  • Wallpaper URLs are injected with JSON.stringify, not quotes — a URL containing a quote character used to break the whole background.

Deliberately unfinished

These are wired but empty, so you know what you are picking up:

  • Fishing has no Lua backing yet; it runs on mock data and is read-only.
  • Lifeinvader reposts are counted in the UI but have no table.
  • Lifeinvader live is read-only; nothing marks a player as streaming.
  • Bank Bills and Loans are placeholder tabs. Finance is fully wired.
  • Voice notes are a UI shell. NUI has no microphone, so releasing the record button fires royal-phone:client:voiceMessage with a duration and sends a placeholder bubble. Hook a voice resource to that event to capture real audio.
  • Documents are not live-synced. Two people editing the same document at once will each overwrite the other on save, because the phone fetches data once per open and never polls. Making it collaborative needs a push channel.
